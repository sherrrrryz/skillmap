1. What is a skill?

An AI agent skill is a folder of instructions (and optionally scripts and reference files) that an agent loads when a task matches the skill's description. Think of it as an onboarding guide for a new hire: you don't retrain the model, you hand it a written procedure for one kind of job.

Without a skill

You paste the same 40-line instructions into every chat, or the agent guesses your preferences every time.

With a skill

The agent sees a one-line description, recognizes when it applies, and loads the full procedure on its own.

Portable

The format is an open standard (agentskills.io), so the same folder can work in Claude Code, other coding agents, and more.

Sources: Anthropic engineering post, Agent Skills specification.

2. Anatomy of a skill

Startup: name + description loaded
→
Task matches: full SKILL.md loaded
→
Needed only: scripts/ references/ assets/

This is progressive disclosure: the agent pays a small token cost for every skill (metadata), a bigger cost only for the skill it actually uses (body), and loads extra files only when a step needs them.

< 5,000 tokens recommended

├── scripts/        # Optional: code the agent can run
├── references/     # Optional: long docs loaded only when needed

IndividualPersonal workflow

Writing style, code review checklist, your company's report format. Stored in ~/.claude/skills/ or similar.

TeamShared in a repo

4. Write your first skill (step by step)

1

Pick one repeatable task

Good: "turn meeting notes into action items". Too broad: "help me with work". A skill should be something you do again and again.

2

Do the task once with the agent, then write down what you corrected

Your corrections are the most valuable part. They are the rules your skill needs.

3

Write the SKILL.md

Keep the body short. Claude is already smart; only add what it does not know: your format, your tools, your rules.

4

Test with 3 real prompts

Anthropic's guide recommends at least three evaluations. Test with the models you actually use.

5

Iterate from failures

When the agent misses, add the missing rule. When it over-applies, narrow the description.

Example: a small, good skill

---
name: meeting-action-items
description: Turns meeting notes into a table of decisions, owners and due dates. Use when the user pastes meeting notes or asks for action items, follow-ups or a recap.
---

# Meeting action items

1. List decisions first, one per line, in past tense.
2. For each action: owner (name, or "UNASSIGNED"), task (verb first), due date (or "NONE").
3. If a date is relative ("next Friday"), convert it using today's date and state the exact date.
4. End with a list of open questions. Do not invent owners or dates.

## Output format
| # | Owner | Task | Due |
|---|-------|------|-----|

Why it works: the description contains the words the user will say ("meeting notes", "action items"), the steps are specific, and it forbids the one mistake people hate (invented owners).

Good vs. weak description

Weak
description: Helps with meetings.

The agent cannot tell when to load it.

Strong
description: Turns meeting notes into action items with owners and due dates. Use when the user pastes notes or asks for a recap.

Says what, when, and which keywords trigger it.

5. How to grow a skill over time

Most good skills are not written in one go. They evolve through a loop:

Use it
→
Notice a correction
→
Add the rule
→
Test on past cases
→
Move big parts to references/
Stage A: Plain prompt. One Markdown file, a few rules. Fine for a week of use.
Stage B: Structured skill. Clear steps, output template, examples of good and bad output.
Stage C: Skill with resources. Scripts for fragile steps (e.g. a validator), references for long specs.
Stage D: Tested and shared. Eval cases, versioned in git, used by a team or published.

Design principles to check against

  • Concise: every paragraph should justify its token cost.
  • Match freedom to risk: text guidance for judgment calls; exact scripts for fragile steps (e.g. database migrations).
  • One level of references: SKILL.md links to files; those files should not link further.
  • Keep SKILL.md under ~500 lines.
  • Avoid time-sensitive facts in the body; put old patterns in a clearly marked section.

Sources: Skill authoring best practices, Agent Skills specification.

6. Skills in automated workflows

A skill tells the agent how to do a task. Automation decides when it runs and what happens around it. Claude Code's docs and Anthropic's guide describe several layers that work together:

Skill (know-how). Loaded when relevant or invoked by name like /deploy. Holds the procedure.
Subagent (isolation). Runs the skill in its own context and returns only a summary. Good for parallel work and keeping the main chat clean.
Hook (deterministic trigger). A shell command, HTTP call or prompt that runs on a lifecycle event (e.g. after an edit, before a command). Always runs; the model does not have to choose it.
Scheduler / script (time trigger). A cron job or managed agent that runs the skill every day, like a daily digest.
MCP (connection). Gives the agent access to external services (Notion, Gmail, databases). Skills tell it what to do with those tools.

Example pipeline: weekly KPI report

Cron: Monday 9am
→
Skill: weekly-kpi-report
→
Subagent: pull CSV
→
Hook: validate output
→
Publish via MCP

Automation patterns people use

PatternWhat it looks likeRole of the skill
Plan → execute → verifywriting-plans, then executing-plans, then a verification passEach step is a skill with a checklist
Parallel fan-outSeveral subagents each handle one part of a taskDefines the job each subagent does
Scheduled digestCron searches sources and writes a summary to a pageHolds the format, sources and rules for the digest
Event-driven checkA hook runs a linter after every file editThe hook is deterministic; the skill explains how to fix the errors
Autonomous loopAgent works through a task list, commits passing work, retries failuresEach item follows the same skill; verification gates completion

Rule of thumb

Use a skill for procedures you want the model to follow with judgment. Use a hook for things that must always happen. Use a subagent for work that should not flood your main context. Put a schedule around the skill when it should run without you.
